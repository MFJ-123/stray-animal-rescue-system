# 跨模块契约清单

这是 G0 需要落实到 Java 接口和 DTO 的业务契约清单，方法名称仅为建议，不代表源码已实现。提供方负责契约与实现，调用方共同评审；具体签名和状态枚举确认后记录在仓库。操作者使用可信服务端上下文，不能直接接受前端伪造的身份。

当前协作设计以[概要设计说明书（评阅修订版）](design/流浪动物救助系统_系统概要设计说明书（评阅修订版）.docx)为准。包依赖见第 6 章，接口方法中的相对路径统一加 `/api/v1`。A 已交付公共权限、命令处理、审计和事件接口，其 Java 签名以本仓库的接入说明和源码为准。

A的CurrentAccess、ObjectAuthorization/ObjectPolicy、IdempotencyService、Versions及ResponsibilityProvider现已提供，实际签名、事务锁序和前端用法见[公共机制接入](公共权限与接口接入说明.md)及[账户接入](账户与资格接入说明.md)。AuditWriter、AuditService、OutboxService与OutboxHandler已提供，供业务方和E按[审计事件接入说明](审计与事件接入说明.md)调用；其余建议服务仍待各提供方实现。

| 提供方 | 调用方 | 建议服务能力 | 核心输入及返回 | 一致性要求 |
| --- | --- | --- | --- | --- |
| A Access | B/C/D/E | requirePermission、checkVolunteer | 会话上下文、对象与动作；允许或明确拒绝 | 每次写入复查权限，资格暂停与新认领/指派使用一致锁规则 |

### SAR-SYS-0014 认领与协作报名

三项接口由 B 的救助任务包实现。操作者从 A 提供的服务端会话取得。

| 方法和相对路径 | 路径编号 | 必填请求正文 | 成功返回 |
| --- | --- | --- | --- |
| `POST /tasks/{id}/claim` | 任务编号 | `expectedVersion` 为任务版本，另传 `requestKey` | `taskId`、`ownerId`、`state`、`version` |
| `POST /tasks/{id}/participants` | 任务编号 | `requestKey` | `participantId`、`state`（待确认）、`version` |
| `POST /participants/{id}/confirm` | 报名编号 | `expectedVersion` 为报名版本 | `participantId`、`state`（已确认）、`version` |

已有负责人、版本冲突或已满员时返回 409 和当前状态。确认报名时复核负责人身份与剩余协作名额。

### SAR-SYS-0024 死亡核实与归档

C4 保存核实结论并在确认死亡后阻断新业务。归档请求中，C4 检查本包的照护交接，向 C3 查询救助任务结清结果，向 C5 查询申请、预约、预留和领养关系的结清结果，向 C6 查询退养与回访的结清结果。各包处理自己持有的记录。C4 汇总检查结果，全部结清时归档，否则返回未结项。永久档案编号及历史继续保留。

契约评审时须补齐事务入口、读取与加锁方式、重试键、唯一约束、异常传播方式和测试实现的隔离方式。跨包多步操作由协调方调用各包的查询或单项更新服务，避免 Spring 依赖循环。

先冻结契约再并行实现。在 G2 只通过正常新用户路径不能证明信用限制已经完成；G3 必须以真实信用与资格实现替换测试假对象，并执行 TC-15、TC-18—21 等边界测试。
