# 流浪动物救助系统五人分工与集成方案

本方案面向组长和四位组员，依据现有《系统需求规格说明书 V1.2 修订版》和《系统概要设计说明书》制定。建议采用一个公开 GitHub 仓库、一套前端、一套后端和一套数据库结构，按业务分配开发任务。每人交付自己负责业务的页面、接口、数据库变更、测试和说明，并持续合并到共同主分支。

成员暂记为 A（组长）、B、C、D、E。分配不依赖个人技术特长，不设开发周期。以下顺序表示依赖和验收关卡，不是日期安排。现有需求和设计是功能基线，本方案补充代码责任、协作和集成规则；新增规则需全员知晓，不能借分工删减原需求。

## 2 每个人具体做什么

### A 组长负责基础工程和账户访问

1. 建立 Vue 3 与 Java 17 / Spring Boot 统一工程，锁定依赖，配置 MySQL 8.4、统一启动、测试和打包入口。发布时由 Spring Boot 提供前端页面和 HTTPS 接口。
2. 实现注册、登录、退出、失效会话、失败次数与来源频率限制、志愿者资格申请和审核、管理角色配置、资格暂停及对象授权公共机制。
3. 提供公共会话获取、权限校验入口、统一异常和返回体、请求号、幂等处理、公共测试账号及测试时钟接入约定。
4. 提供审计追加、审计查询、事务内 outbox 写入及事件领取/重试机制。各业务负责人补齐自己操作的审计内容和事件；E 实现收件人解析和站内消息落库。
5. 管理主分支、共享配置、依赖版本和发布包。组织接口变更评审，汇总阻塞项与验收结论。

**必须说清的边界：**0005 的浏览筛选由 A 保证入口与统一约定，B 实现线索列表、C 实现公开动物列表；0006 的公共校验机制由 A 提供，各模块负责人实现对象归属检查和字段脱敏。A 不代替所有成员写权限代码。暂停资格由 A 牵头，B/C/E 提供未结责任查询和交接结果，暂停与认领/指派必须使用一致的资格锁约定。

**交付标准：**B—E 能直接复用登录和接口框架；权限撤销后旧页面及旧消息入口也被拒绝；错误返回请求号；审计和业务变更一致提交，回滚后不遗留虚假的成功审计。

### B 负责线索到救助验收

实现线索上报、补充、撤回、核实、重复关联、关注、关闭；实现任务创建、认领、报名确认/撤回、执行、转派、验收、取消及未认领提醒。交付普通用户、志愿者、救助管理员的对应页面，不能只有管理员页面。

拥有 clue、clue_follow、rescue_task、participant、task_animal 的写入服务。task_animal 虽连接动物，也由 B 负责；C 提供动物存在、状态和访问权限查询。不得为通过任务验收而建立虚假动物档案，允许按基线记录未建档原因。

**交付标准：**同一主线索最多一项未结任务；100 个并发认领最多一名负责人成功；负责人最多承担 3 项未终结任务，任务协作者上限按设计取 0—5；转派后旧负责人不能继续写入；报名撤回、重新报名和历史保留正确。不要把“每个任务最多 5 名协作者”误写成其他配额。

### C 负责动物照护和附件

实现动物永久编号、任务关联查询、照护及就诊摘要、照护双方确认、公开资料与领养条件版本发布、暂停/恢复展示、死亡报告核实及归档。提供 B/D/E 所需的动物检查、当前照护查询和责任变更服务。

同时实现附件上传、受控下载、临时附件清理、公开图片移除定位信息和前端图片组件。公开副本与原件权限不同；附件只用编号连接业务，不能把本机文件路径暴露给前端。

**交付标准：**单方确认不改变照护责任；未结照护交接阻止领养交接；照片 1—6 张、单张不超过 5 MB、JPEG/PNG 实际解码通过；归档前显示并处理未结业务；确认死亡后立即阻止新的发布、申请和交接。C 牵头死亡业务，D/E/B 分别处理自己所属的历史与未结事项。

### D 负责领养申请和交接

实现申请提交、补充、撤回、审核沟通、竞争预留、到期释放、条件版本确认及双向领养交接。拥有 application、reservation、handover、adoption 及审核记录等写入服务；条件版本内容归 C，申请人确认记录归 D。

由 D 组织领养交接这一外层事务：调用 A 的授权与资格机制，调用 C 校验/变更动物及照护责任，调用 E 创建回访，调用 A 的审计和 outbox。到期扫描与页面操作使用同一业务服务，不能各写一套规则。

**交付标准：**一只动物仅一份有效预留；预留 7 个自然日，到期优先于旧页面确认；单方确认不生成领养；双方确认成功仅生成一条领养、三条回访，终止其余未结申请；任一步失败整体回滚。申请材料、查询和导出均按对象权限过滤。

### E 负责退养回访和运营

实现三次回访计划、到期/逾期提醒、反馈及核验、异常跟进、退养申请/撤销/实际接回、本人历史、信用事件去重、人工限制与复核。回访期限按交接后 7、30、90 日，逾期是独立标记。

实现站内消息、未读数、举报处置、统计和脱敏导出。消息消费使用 A 提供的 outbox 机制，按收件人和事件键去重。统计通过各业务包提供的查询接口取得一致口径，不另造一套业务状态。

**交付标准：**未实际接回仍保留当前领养关系；接回后通过 D 结束领养、通过 C 恢复照护，并取消未结回访；重复事件不重复通知；合理退养和累计事件只触发人工复核，不能自动处罚；解除限制允许新申请，不能复活已经终止的旧申请。E 组织联合测试，各成员修复本模块问题，E 不包揽全组测试工作。

## 3 仓库与目录划分

仓库确定为 `MFJ-123/stray-animal-rescue-system`，公开（Public）。一个仓库包含前后端、数据库迁移、部署脚本、测试与文档。各人本机有独立数据库，使用同一套迁移和测试数据；不让五人同时修改同一套开发数据。

```text
stray-animal-rescue-system/
  frontend/src/
    views/{access,clue,rescue,animalcare,adoption,followup,operations}/
    api/                    # 按相同业务分文件，公共请求客户端由 A 维护
    router/modules/         # 按业务拆路由，路由汇总由 A 维护
    components/             # 公共基础组件 A；附件组件 C
  backend/src/main/java/cn/edu/sar/
    web/{access,clue,rescue,animalcare,adoption,followup,operations}/
    jobs/                   # 调度入口按业务归各负责人
    domain/{access,clue,rescue,animalcare,adoption,followup,operations}/
    persistence/            # 子包按业务与表归属拆分
    common/                 # 小型通用设施，A 维护
  backend/src/main/resources/
  backend/src/test/
  db/migration/             # 唯一 SQL 迁移源，D 登记编号，各人写自己的变更
  db/seed/                  # 可重复建立的虚构演示数据
  deploy/                   # 配置样例、打包、启停、备份与恢复
  tests/                    # 跨模块、并发、权限、性能测试及说明
  docs/                     # 方案、基线、契约、追踪表、验收证据
  .github/                  # PR 模板、Issue 模板与自动检查
```

表现层是前端；web/jobs 是接入层；domain 是业务层；persistence 是持久化层。依赖沿这个方向调用。业务层不能依赖控制器；控制器不直接操作数据库；不同业务包不能直接修改对方的表。common 只放响应、请求上下文等通用能力，不堆放所有业务。

仓库初始化资料目前提供目录说明和协作模板，**还没有应用源码，不能直接启动系统**。A 完成工程骨架关卡后才有可运行版本。不得把资料检查通过当作业务实现完成。

## 4 开发前先冻结的公共约定

### 4.1 技术和构建

沿用 Vue 3、Java 17、Spring Boot、MySQL 8.4 / InnoDB 和本地私有附件目录。具体 Spring Boot、Node/npm、Maven、数据库驱动及持久化库版本由 A 在初始化时选定、实际构建验证并写入版本清单；统一 package-lock.json 与 Maven Wrapper，其他成员不自行升级或混用持久化框架。

开发时前后端可分别启动，通过统一代理访问接口；Cookie 会话及跨源策略由 A 配置。交付时构建前端并打包进后端，使用同源 HTTPS；证书私钥、真实密码、真实附件和数据库导出不提交 Git。成员用示例配置自行填写本机配置，演示数据只使用虚构信息。

### 4.2 接口契约

统一 `/api/v1` 前缀；编号通过 JSON 传字符串，数据库为 bigint；统一返回 `code、message、requestId、data`。400 表示输入错误，401 会话失效，403 无权限，409 状态或版本冲突，503 暂时不可用。每个接口的具体业务码和 data 字段需在契约中定义。

每个接口在同一条目内写明：调用角色及对象权限、A/B/C 场景与处理结果、请求及返回字段、传输方式、状态变化、事务范围、幂等规则和测试用例。不要重新拆成两套独立的“输入接口”和“输出接口”。先用模板登记，再由提供方和调用方共同确认；补齐机器可读 OpenAPI 契约及示例后进行自动校验。

创建及确认使用 requestKey，受控更新使用 expectedVersion。一次用户意图遇到网络失败时复用原键，相同键异参返回冲突；用户修改内容或发起新操作才使用新键。UI 禁用按钮只能改善体验，服务端必须再次鉴权和校验当前状态。

操作者从服务端会话读取，不能相信前端提交的 userId 就是操作者。所有涉及对象的查询、附件和历史链接重新授权。客户端不自行决定到期；服务端统一时钟，接口含时区，数据库 DATETIME(6) 保存 UTC，展示按 Asia/Shanghai。期限计算遵循需求中的自然日规则，测试通过可控时钟推进，不能让各人各自硬编码当前时间。

### 4.3 数据库与迁移

各负责人提出自己表的字段、索引和外键；D 管理迁移登记，A 和受影响负责人审核跨表变更。表归属详见数据边界表。已在共享环境执行的迁移不能修改或重命名，新增修复迁移；合并前检查从空库建立和从上一版本升级两条路径。生产式改表不依赖自动建表功能。

迁移文件示例 `V001__foundation.sql`、`V002__clue_and_task.sql`。这是命名示例，不预分配真实编号。D 为待合并变更分配下一编号，并按外键依赖确定顺序，避免两个人都提交 V005。演示种子数据与结构迁移分开，不把删库重建脚本用于升级。

`db/migration/` 是唯一 SQL 源；A 将其纳入后端构建资源和迁移执行配置，不手工维护第二份副本。项目不能到最后再通过五份数据库导出拼接。

## 5 跨模块如何整合

### 5.1 先确定接口，再并行实现

提供方在自己的业务包暴露小型 Java 服务接口及必要 DTO，调用方依赖这些契约，不依赖对方控制器或数据库实体。接口先合并、实现可随后完成；测试中允许假实现，但正式启动和验收不能启用“默认成功”的假服务。

同一 Spring Boot 进程内调用 Java 服务，不为这次课程项目拆成七个 HTTP 服务。对于 C2 与 C3、C5 与 C6 的双向业务关系，用各自清晰的查询接口和原子操作接口解耦：查询服务不要反过来依赖调用者的编排服务，避免构造器循环依赖。不要靠允许循环引用解决设计问题。

### 5.2 关键联合场景和牵头人

| 场景 | 牵头 | 配合人 | 必须一起验收的结果 |
| --- | --- | --- | --- |
| 线索核实与任务创建/认领 | B | A | 资格有效、配额有效，同主线索未结任务唯一，同任务只有一位负责人 |
| 任务验收关联动物 | B | C | 档案存在且有权关联；未知动物按需求保留未建档原因 |
| 暂停志愿者资格 | A | B、C、E | 未结任务、照护、回访和协作责任处理完才暂停；并发新认领不能绕过 |
| 双方领养交接 | D | A、C、E | 资格/版本/期限/照护检查通过，领养、责任、回访、审计和待投递事件一致提交 |
| 退养实际接回 | E | C、D、A | 结束当前领养，恢复照护，取消未结回访，保留历史；未接回不能提前转状态 |
| 死亡核实与归档 | C | B、D、E、A | 核实后禁新业务；按基线清理未结事项后归档；已领养死亡无需虚构退养接回 |
| 人工限制领养资格 | E | D、A | 清理未结申请与预约、释放预留；旧页面提交/审核/交接均拒绝，退养和回访仍可用 |
| 暂停领养发布 | C | D、E | 对已预留先解除并终止对应申请；其他在审申请按需求保留和通知 |
| 业务成功后的通知 | E | A、各业务负责人 | 业务提交后消费；收件人和事件键去重；失败重试不撤销业务事实 |

这些牵头关系不赋予跨表随意写入权。牵头人拥有业务编排，数据所属人提供服务并参加评审。死亡核实和归档可能是分阶段流程，不能为图省事一次删除所有未结记录。

### 5.3 事务和并发约定

领养交接、退养接回等单次原子业务，由牵头服务开启外层事务，各包写入使用同一数据源并加入该事务。审计和 outbox 登记在同一事务内；关键子步骤不能另开独立提交的事务，也不能放到异步线程中后补关键关系。

调用中途故障必须整体回滚。测试要主动在“已经变更动物、尚未建立回访”等位置制造失败，并检查所有相关表；不能只看接口返回失败。业务提交后的消息投递单独重试，失败不回滚已经成功的领养。

所有并发路径必须遵循共同锁顺序。A/D 汇总涉及的资格、动物、主线索、任务、申请等锁资源，形成逐场景锁清单；需要多行同类锁时按编号排序。未确认跨场景顺序前，不能各自随意添加锁。使用同一锁顺序加数据库唯一约束，死锁出现时回滚并仅对可安全重试的整个命令有限重试，复用幂等键。

当前领养、未释放预留、未结任务等唯一性按 MySQL 设计实现。不能直接依赖 PostgreSQL 的部分索引语法；到期条件不能写成依赖当前时间的生成列。预留是否有效应先依据服务端时间处理到期和释放，再做事务检查，定时扫描只是补偿。

## 6 GitHub 的实际协作方式

### 6.1 仓库建立和权限

仓库归组长账号 MFJ-123，名称 `stray-animal-rescue-system`，可见性为 Public。四位成员作为协作者加入；无需五个仓库互相复制，也不交换 GitHub 密码或令牌。本地初始化资料已经准备，远端公开仓库已创建，协作者邀请尚未执行。

远端仓库已经创建。资料导入 main 后，配置协作者、Issue 和规则。用户名尚未提供，因此暂用 A—E，不能把占位符当成真实 GitHub 用户去邀请。

仓库按组长要求设为公开（Public）。目前没有预设开源许可证，许可证选择单独记录，不因设置 Public 自动添加。

### 6.2 分支和合并

采用 `main + 短期功能分支 + 发布标签`。main 始终保留通过验证的集成版本；不额外设长期 develop，也不让每人长期维护一份完整系统。

分支按任务命名，例如 `feat/0014-task-claim`、`fix/0029-handover-retry`。一个 PR 对应一个可验收变化；大功能拆为契约、数据库、服务、页面等小批次，未接通的功能不在正常菜单展示。成员每天开始工作前同步主分支，完成可测试小块就提交 PR，不攒到全部功能结束。

PR 写清需求号、改动行为、受影响接口和表、实际测试命令/结果及页面证据。至少由一名非作者评审；跨模块变更还需受影响模块负责人同意。A 合并发布；A 自己的代码由 D 或相关负责人评审，不自行替代评审。默认使用 squash merge，保留任务号与变更说明，合并后删除已完成分支。

冲突由变更作者与文件负责人共同处理，解决后重新运行相关测试。不能一键“全部使用我的版本”，不能覆盖别人目录，不能向共享主分支强制推送。main 发生回归时先修复或 revert 有问题的合并，再推进其他集成。

### 6.3 共享文件如何避免冲突

package.json、package-lock.json、pom.xml、启动类、公共配置、根路由、统一请求客户端、CI 和发布脚本由 A 负责合并。成员需要改依赖时，在 PR 说明原因，由 A 统一处理；成员业务路由放在自己的模块文件，不同时修改一份巨大路由表。

每个 SQL 迁移文件只有一个作者。D 登记编号和顺序，作者提交 SQL；组员不能用自己的全库导出覆盖现有结构。两份 Word 基线由 A 管理修订，成员通过变更记录提交意见，不并发直接编辑同一个二进制文档。PPT 统一由 A 汇总最新设计与演示证据。

### 6.4 GitHub 设置与费用边界

如果账号套餐支持，给 main 配置必须 PR、至少一名批准、讨论已解决、检查通过、禁止强推及删除，并要求相关负责人评审。CODEOWNERS 只辅助指定评审，不会自动禁止其他成员改文件，也不能替代分支保护。

公开仓库可按 GitHub 官方说明配置受保护分支和 CODEOWNERS。建仓后实际启用 main 分支的评审及检查规则；仅上传模板不会自动启用保护。规则尚未配置时，按“成员提交 PR、组长核对测试后合并”的约定协作。

官方依据：[创建仓库](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository)、[受保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[代码所有者](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)。

## 8 测试责任和完成标准

每人对自己模块提交至少正常、越权、状态冲突、重复请求及事务失败的相关测试。并发与 MySQL 唯一约束必须在 MySQL 8.4 上验证，不能仅靠内存数据库测试代替。复杂期限使用可控时钟，不能等 90 天或修改真实系统时间来验收。

完整用例和归属见 `test-matrix.csv`（21 个 TC），质量指标见 `quality-matrix.csv`（10 项 NFR），功能追踪见 `requirements.csv`（40 项）。这些表初始状态都是待开始/待验证，不表示已经实现或通过。

重点质量职责：A 牵头权限、恢复、可用性、日志与重试规则；B/D 负责认领与预留竞争；E 组织负载、消息时效和验收证据；C 组织界面尺寸、图片与文件恢复；易用性测试由 E 组织至少五名测试者，各成员处理自己的界面问题。

保留原文门槛：4 核/8 GB、RTT≤50 ms；1 万线索/5 千动物/2 万申请；50 并发、10 分钟、90% 查询/10% 写入，非文件请求 P95≤2 秒、5xx＜1%；通知 60 秒内、扫描延迟≤2 分钟；备份每日一次保留 7 份，RPO≤24 小时、RTO≤4 小时。月可用率 99% 是目标，本期只通过故障恢复演练验证能力，不把短期测试写成已达到月度可用率。

单个任务完成必须同时满足：

- 对应需求的页面、接口、权限、状态及数据库变更可用；不适用的层明确说明原因。
- 接口契约和迁移已评审，调用方已接通；正常及关键异常测试通过。
- 审计、消息、附件或定时处理等相关横向能力没有漏接。
- 新检出的代码可构建；没有依赖作者电脑上的私有 SQL 或配置。
- PR 合并，追踪表填写 PR/提交与证据位置，测试由另一人复核。

当前随附自动检查只校验资料与编号覆盖。G1 必须新增真正的前端 lint/测试/构建、后端编译与测试、MySQL 空库迁移及升级测试；G2 后增加主链路冒烟检查。CI 的检查名称应区分“资料检查”和“应用测试”，不能用一个绿色结果掩盖测试尚未建立。

## 9 组长怎样管理而不成为瓶颈

任务用 Issue 跟踪，状态为待开始、进行中、待评审、待联调、已验收。每条任务有唯一主责、需求号、依赖、验收条件和完成证据。CSV 是准备好的任务清单，不会自动变成 GitHub Issue；建仓后再逐条或通过接口建立。

成员同步“已完成什么、下一步是什么、卡在哪里”，阻塞必须落到具体接口或人员。公共问题由 A 裁决技术方案；业务含义先查需求，再查概要设计，有冲突登记变更，不能靠聊天口头覆盖正式要求。

模块负责人先完成本模块自测，再发给调用方联合验证。A 重点检查公共契约、跨模块事务、迁移和发布，不逐行替五个人修代码。E 汇总缺陷与测试证据，问题归属回到负责模块。每个重要模块由另一人做评审，减少某个人缺席就无法维护的风险。

需求或接口变更记录包含：原约定、新约定、受影响需求/页面/调用方/数据库/测试、迁移办法、批准人及关联 PR。已经合并的接口变更必须有调用方同步修改或兼容方案。

## 10 最终合并交付什么

交付一个统一版本，包含：前后端源码、迁移及虚构种子数据、依赖锁定、完整配置示例、可运行 sar.jar、Windows 启停与备份恢复说明、测试及验收证据、两份更新后的 Word 基线、与实现一致的答辩 PPT。Git 仓库存源码和文档，较大的可执行交付包通过 Release 附件保存；不把 target、node_modules、真实照片或数据库运行目录提交到源码历史。

发布前，在另一台电脑从干净检出开始构建和启动；导入虚构数据后走完整主流程；将同批次数据库和附件恢复到独立目录并核对照片及关联；确认权限与并发测试通过。冻结发布提交，标记如 v1.0.0 的版本标签，README 写明实际版本、启动步骤、演示账号获取方式和已知限制。

组长现在只需先把 A—E 对应到真实姓名，并让大家确认各自范围。从远端公开仓库获取本资料，再推进 G0/G1；不要先让五个人各自搭一套系统再来拼接。
