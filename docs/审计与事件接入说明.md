# 审计与事件接入说明

范围：A部分第4项及T05，提供事务内审计、按职责查询、追加纠错、outbox登记、后台领取、失败重试和中断恢复。E负责接收人判断、站内消息入库及消息页面；B/C/D/E在自己的业务服务中调用这里的公共服务。未接入的处理类型保持待处理。

## 1 页面与权限

管理员登录后进入“消息与运营”，也可用侧栏“操作审计”和“事件投递监控”。前端菜单只控制显示，后端每次查询、追加和幂等重放都会重新校验角色。

| 角色 | 审计可见范围 | 事件监控及人工重试 |
| --- | --- | --- |
| SYSTEM_ADMIN | 全站脱敏摘要，不因此获得业务原始材料访问权 | 允许 |
| RESCUE_ADMIN | RESCUE、ANIMALCARE，以及ACCESS下资格申请、审核、暂停的记录及其纠错说明 | 不允许 |
| ADOPTION_ADMIN | ADOPTION、FOLLOWUP及其纠错说明 | 不允许 |
| 兼任管理角色 | 上述职责范围取并集 | 需兼任SYSTEM_ADMIN |
| 普通用户、仅志愿者或未登录 | 普通用户及志愿者403；未登录401 | 拒绝 |

模块和动作由后端业务代码确定，不取自浏览器。查询先在SQL限制职责再分页；详情与纠错使用同一范围。对职责外的记录返回404，避免透露存在性。修订记录沿用原记录范围，不能通过关联记录扩大权限。

## 2 浏览器接口（请求与返回放在同一条目）

所有路径前缀/api/v1，沿用同源会话、写入CSRF和code/message/requestId/data。时间为ISO带时区字符串，编号为字符串；page默认1、pageSize默认20且最多50。

### GET /audit-logs 与 GET /audit-logs/{id}

A. 授权管理员查询：可按module、objectType、objectId、requestId、from、to筛选，条件为AND；from含边界、to不含边界。以createdAt和id倒序分页。详情返回原始记录及其关联纠错列表。

B. 重复查询：读取当前职责范围；角色变化立即影响后续请求。筛选无结果返回空items，不泄露职责外数量。选择一条纠错记录时，详情回到它关联的原记录。

C. 未登录401、无管理角色403、范围外详情404；无效筛选、倒置时间或分页越界400；数据库故障503。查询不返回密码、令牌或申请材料。

请求字段为上述筛选及分页参数，均为可选；objectId必须正数，module为ACCESS/RESCUE/ANIMALCARE/ADOPTION/FOLLOWUP/OPERATIONS。返回分页items/total/page/pageSize；每条包含id、actorId、module、objectType、objectId、action、beforeState、afterState、reason、requestId、createdAt、correctsId。详情为record和corrections。actorId=0仅用于服务端系统动作，正数对应账户编号；界面不推断额外身份信息。

### POST /audit-logs/{id}/corrections

A. 在本人职责范围的原始记录下，提交reason（10—500字）及requestKey（8—64位，UUID推荐），追加关联纠错记录及AUDIT_CORRECTED事件；返回新增审计DTO。

B. 同操作者、同键同参返回首次新增记录，不重复追加；同键异参409。对纠错记录再次纠错返回409，须选择原始记录。每次网络请求仍有自己的requestId。

C. 无权限、范围外或原记录不存在分别403/404；字段不合法400；任一写入失败整体回滚。没有更新或删除审计的接口，PATCH/DELETE不会覆盖历史。追加说明不会自动改动任务、领养等业务状态；实际状态纠正应由所属业务服务执行专用修订或撤销流程，并追加审计。

### GET /outbox-events

A. 系统管理员按status和分页查看事件摘要，返回events分页、counts各状态数量、oldestPendingAt最早未完成时刻、registeredConsumers已接入类型。

B. 可刷新读取处理结果；PENDING且没有对应服务的事件继续保留。counts和最早时刻为查询时观测值，后台并发处理时下一次刷新可能变化。

C. 未登录401、非系统管理员403、无效状态或分页400、依赖故障503。摘要包含id、eventType、objectType、objectId、status、attempts、availableAt、leaseUntil、lastError、createdAt；不暴露payload、领取令牌或内容摘要。

### POST /outbox-events/{id}/retry

A. 系统管理员提交reason及requestKey，将RETRY或DEAD事件恢复PENDING，清零领取次数、清除旧租约，并追加EVENT_RETRY_REQUESTED审计。

B. 同键同参复用登记结果，审计只追加一次；异参409。返回首次登记时的事件摘要快照，页面再读取当前状态。权限撤销后即使同键也拒绝重放。

C. PENDING、PROCESSING、DONE均409，不能通过此入口重新投递已完成事件；不存在404，其他权限和字段错误同上。缺失消费者时人工登记也不会虚构成功。

## 3 业务方写入审计及事件

源码在backend/src/main/java/cn/edu/sar/domain/operations。AuditWriter.append(Change)与OutboxService.append(...)都要求已有事务（MANDATORY），避免先改业务后单独写日志。AuditWriter使用注入Clock自动确定服务端时刻，返回审计编号。

Change包含actorId、module、objectType、objectId、action、beforeState、afterState、reason、requestId。actorId必须来自会话或可信后台上下文，不能用前端字段代替。module取上表枚举；objectType及action为后端固定的大写代码，长度最多32/48。快照只接受状态码、编号和结构分隔符，最多500字；不保存联系方式、精确位置、密码、令牌或原始申请材料。reason是经过筛选的业务摘要，公共层还会遮蔽常见手机号/号码、邮箱、坐标及显式凭据赋值。业务负责人仍须选择摘要，不能把表单或完整对象直接作为日志内容。

示例（在已注入audits/events的业务Spring服务中）：

```java
@Transactional
public void completeChange(long actor, long objectId, String requestId) {
    // 在这里先校验角色、对象、版本和状态，并写本模块业务数据。
    long auditId = audits.append(new AuditWriter.Change(actor, "RESCUE", "TASK", objectId,
        "TASK_COMPLETED", "PENDING_ACCEPTANCE", "COMPLETED", "管理员确认救助验收完成", requestId));
    events.append("TASK:" + objectId + ":COMPLETED:V1", "TASK_COMPLETED", "TASK", objectId,
        Map.of("actorId", Long.toString(actor), "auditId", Long.toString(auditId), "status", "COMPLETED"));
}
```

此片段说明调用顺序，不代表任务功能已经实现。actor锁、业务对象锁、审计/outbox按既定顺序办理，多对象锁顺序由业务双方确认；不要在消费者中嵌套另一生产命令。

事件键是该事实的稳定标识，8—96位字母、数字、下划线、点、冒号或连字符，区分大小写；不能每次重试都新生成。它在全站唯一，建议“业务类型:编号:事实:版本”。同键同内容复用，类型/对象/正文改变时409 / EVENT_KEY_CONFLICT。内容以排序后的字段形成SHA-256，比较使用当前锁定读，已有事务快照也不能误读旧事件。

事件正文最多20个引用字段，只接受以Id结尾的编号（如actorId、auditId、applicationId）、version数字和status/decision/reasonCode大写状态码。不携带自由文本、收件人联系方式、申请全文或附件路径。需要了解详情时由消费者通过所属服务查询，禁止绕过对象权限。角色变化、密码修改、资格申请/审核/暂停和首次管理员初始化已实际登记ACCESS_CHANGED；旧V001—V004历史不补发通知。纠错登记AUDIT_CORRECTED。

## 4 E如何接入消息处理

实现OutboxHandler作为Spring Bean：eventType()返回一个固定类型，handle(Event)完成接收人判断和消息入库。一个类型只能有一个Bean，重复注册启动失败；多个业务类型分别注册。生产代码当前没有假的消息消费者。

后台默认每5秒扫描，每轮最多20条，只领取已注册类型；可设SAR_OUTBOX_ENABLED=false关闭扫描。登记事件不依赖消费者是否就绪，未注册类型保留PENDING，安装对应Bean并重启后即可处理。

E必须在同一数据库事务内生成站内消息，消息表以“事件编号＋收件人编号”设唯一约束。不要在handle里开启REQUIRES_NEW、发送邮件、访问HTTP服务或执行无法回滚的外部副作用。局部DB写入与DONE确认同事务提交；任一步失败，两者一起回滚。读取当前业务确定接收人，事件不得直接授予用户查看旧业务材料的权限；消息跳转时重新鉴权。

若经当前业务规则判定没有合法接收人，可以在完成真实判断后正常返回；不能因为业务服务缺失或异常而吞掉错误。依赖不可用应抛异常，由后台重试。消费者无需自己修改outbox状态或处理领取令牌。

## 5 领取、失败和恢复规则

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| PENDING | 已提交、等待服务处理 | 仅注册类型能领取 |
| PROCESSING | 已领取，有唯一令牌和60秒租期 | 消费及确认持有事件行锁；租期过后可回收 |
| RETRY | 消费失败且未达到上限 | 5、10、20…秒指数退避，最大3600秒 |
| DEAD | 领取后失败次数累计达到8次 | 保留记录，管理员处理原因后登记重试 |
| DONE | 消费和确认已一起提交 | 不再次领取或人工重置 |

领取在独立短事务中使用FOR UPDATE SKIP LOCKED，多进程可领取不同事件。并发扫描时，某次轮询可能因候选行暂被锁定而返回空，后续扫描继续领取，不能把单次空结果当成永久无事件。消费前验证令牌及未过期租约，并在事务中锁住事件行；成功时写DONE。失败时先回滚消费者事务，再用独立事务登记RETRY/DEAD，只保存通用错误码CONSUMER_FAILED，不保存异常原文。数据库短暂故障由后续扫描恢复。

进程在领取后退出，事件保留PROCESSING；租期到达后被重新领取。重新领取生成新令牌，旧工作线程不能确认它。消费执行超过租期时当前事务回滚，后续重新处理；消费者须把单个事件处理控制在60秒内。业务成功记录和outbox都在同一数据库，重启后继续扫描，无内存队列丢失问题。

这是至少一次交付机制；本地数据库副作用与确认绑定，仍要求E设置消息唯一约束。不得据此声称邮件等外部操作有严格一次保证。后台内部接口不提供给浏览器，管理员页面只有查询和受控重试。

依据：[MySQL 8.0锁定读与SKIP LOCKED](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)、[Spring 6.2任务调度](https://docs.spring.io/spring-framework/reference/6.2/integration/scheduling.html)。

## 6 迁移与交付边界

V005为audit_log增加module及corrects_id，追加outbox_event和索引；V001—V004保持原样。下一个迁移编号从V006登记。当前审计按接口只追加，没有覆盖或删除入口；数据库维护账号的管理权限不属于业务页面权限。审计按需求保留两年，本次不提供自动物理清理；后续维护任务须按保留及备份规则审批执行。
